🎯 Vue d'ensemble

TransBooking BF est une plateforme SaaS multi-tenant de gestion du transport interurbain au Burkina Faso. Cette API REST alimente les applications web et mobiles de cinq acteurs : super admin, administrateur de compagnie, agent guichet, contrôleur et voyageur.

🚀 Caractéristiques principales

  • Authentification JWT (SimpleJWT) avec rotation et blacklist des tokens.
  • Isolation multi-tenant stricte : chaque compagnie ne voit que ses données.
  • Mode hors ligne : les agents vendent sans internet, synchronisation différée.
  • Réservation concurrente sûre via verrou de ligne select_for_update().
  • QR code & billet PDF encodant le ticket_number, jamais l'id DB.
  • Rate limiting sur les endpoints d'authentification.
  • Export des réservations en Excel / PDF / CSV.

/api/v1/Espace voyageur authentifiéVoyageur

/api/v1/company/Administration compagnieCompany admin

Base URL de développement : http://localhost:8000. Toutes les URLs de cette page sont relatives à /api/v1/.

En-têtes requis

Content-Type: application/json
Authorization: Bearer <access_token>   # sauf endpoints publics

Pagination

Les collections renvoient une enveloppe paginée :

{
  "count": 128,
  "next": "http://localhost:8000/api/v1/bookings/?page=2",
  "previous": null,
  "results": [ /* … */ ]
}

Format d'erreur

Les erreurs suivent le format standard DRF : soit un objet par champ, soit une clé detail.

// Erreur de validation (400)
{ "phone": ["Ce numero de telephone est deja utilise."] }

// Erreur métier / permission (403, 404, 409, 410)
{ "detail": "Ce voyage est complet." }

🔐 Authentification (JWT)

L'API utilise des JSON Web Tokens. Le flux est : se connecter pour obtenir une paire access / refresh, envoyer l'access dans l'en-tête Authorization, puis le renouveler via refresh avant expiration.

1. POST /auth/register/       → crée un compte voyageur
2. POST /auth/login/          → { access, refresh, role, prenom }
3. Authorization: Bearer <access>   sur chaque requête protégée
4. POST /auth/token/refresh/  → nouvel access (avant expiration)
5. POST /auth/logout/         → blacklist du refresh
Durées recommandées : access court (≈ 15 min), refresh long (≈ 7 jours) avec rotation et blacklist activées.

👥 Rôles & matrice de permissions

Chaque vue déclare explicitement ses permission_classes. Un token valide ne suffit pas : le rôle doit correspondre. Une compagnie suspendue ou rejetée bloque son administrateur.

RôleClassePeut notamment…
voyageurIsVoyageurRéserver, annuler, télécharger son billet
agent_guichetIsAgentGuichetVendre au guichet (online/offline), rechercher un billet
controleurIsControleurScanner un QR, embarquer les passagers
company_adminIsCompanyAdminLister & exporter les réservations de sa compagnie
super_adminIsSuperAdminSupervision transverse de la plateforme
Isolation multi-tenant : tous les get_queryset() filtrent par la compagnie de l'utilisateur courant. Un agent/contrôleur/admin ne peut jamais accéder aux données d'une autre compagnie (réponse 404, jamais 403 pour ne pas révéler l'existence de la ressource).

👤 Module Users

Gestion des comptes et de l'authentification. L'inscription publique crée exclusivement des comptes voyageur ; les comptes agents et administrateurs sont provisionnés en interne.

Identifiant

Le phone (numéro burkinabè validé) est l'identifiant de connexion, pas l'email.

Mot de passe

8 caractères minimum, stocké haché (jamais renvoyé par l'API).

Rôle

Renvoyé dans le token de login pour aiguiller l'interface cliente.

🏭 Module Companies

Ce module gère le cycle de vie des compagnies de transport, unité centrale du modèle multi-tenant : chaque agent, véhicule, trajet, voyage et réservation appartient in fine à une compagnie. Une compagnie traverse plusieurs états — pending (demande à valider), active (opérationnelle), suspended ou rejected (bloquée). Tant qu'une compagnie n'est pas active, son administrateur ne peut rien faire ; dès qu'elle est suspendue, toutes ses opérations sont gelées (la permission IsCompanyAdmin le refuse).

Trois publics interagissent avec ce module : le super admin (création, validation, suspension), le public (annuaire des compagnies actives) et le company admin (paramètres de sa propre compagnie : charte graphique, moyens de paiement, préférences SMS).

🛡️ Super admin — CRUD & workflow de validation

Le super admin dispose d'un CRUD complet sur toutes les compagnies. Il peut créer directement une compagnie (elle est alors active d'emblée) ou traiter les demandes entrantes via un flux d'approbation dédié.

GETPOST PATCHDEL /super/companies/ Super admin

CRUD des compagnies. Filtrable (?status=, etc.). La création applique automatiquement le statut active et vérifie l'unicité du nom.

Champs clés : name, sigle, city, phone, email, responsible_name, rccm, ifu, commission_rate (taux de commission plateforme, en %).

POST /super/companies/{id}/activate/ · /suspend/ Super admin

Réactive ou suspend une compagnie. La suspension accepte un motif (reason) et gèle immédiatement l'accès de son administrateur.

curl -X POST http://localhost:8000/api/v1/super/companies/3/suspend/ \
  -H "Authorization: Bearer <access-super>" \
  -H "Content-Type: application/json" \
  -d '{ "reason": "Documents RCCM expirés" }'
GETPOST /super/company-requests/ · /{id}/approve/ · /{id}/reject/ Super admin

Liste les demandes de création en attente (status = pending) et permet de les approuver (la compagnie devient active) ou de les rejeter avec un motif. C'est le point d'entrée du processus d'accréditation d'un nouveau transporteur.

🌍 Public — annuaire des compagnies

GET /public/companies/ · /public/companies/{id}/ Public

Annuaire public des compagnies actives uniquement. La liste est mise en cache 1h côté serveur. Le détail ajoute le contact (téléphone, email) et, à terme, les avis clients.

Réponse (liste) : id, name, sigle, logo, description, city, rating (note moyenne, quand l'app reviews est branchée).

⚙️ Company admin — paramètres de sa compagnie

Ces trois endpoints opèrent implicitement sur la compagnie de l'administrateur connecté : aucun identifiant n'est passé dans l'URL, la compagnie est déduite du token. Ils illustrent le principe d'isolation « je ne peux configurer que ma propre compagnie ».

GETPATCH /company/settings/ Company admin

Consulte / met à jour l'identité et la charte graphique de la compagnie : name, logo, banner, primary_color, welcome_message, coordonnées et responsable.

GETPATCH /company/settings/payment-methods/ Company admin

Active ou désactive les moyens de paiement acceptés par la compagnie. Le PATCH reçoit une liste [{ "method": "...", "is_active": true }] ; les méthodes inconnues sont ignorées silencieusement.

curl -X PATCH http://localhost:8000/api/v1/company/settings/payment-methods/ \
  -H "Authorization: Bearer <access-admin>" \
  -H "Content-Type: application/json" \
  -d '{ "payment_methods": [
        { "method": "cash", "is_active": true },
        { "method": "orange_money", "is_active": true }
      ] }'
GETPATCH /company/settings/notifications/ Company admin

Active/désactive les SMS automatiques : sms_booking_confirmation (confirmation de réservation), sms_departure_reminder (rappel avant départ), sms_parcel_arrival (arrivée de colis). Créés à la volée avec des valeurs par défaut.

🗺️ Module Geography

Ce module fournit le référentiel géographique du réseau : les villes desservies et les gares (stations) de chaque compagnie. Les villes sont un référentiel partagé par toute la plateforme (créées par le super admin, consultées publiquement), tandis que les gares sont des ressources privées propres à chaque compagnie.

GET /cities/ Public

Liste de toutes les villes desservies (non paginée, cache 1h). Sert à alimenter les listes déroulantes de recherche de voyages. Réponse : id, name, region.

GETPOST /super/cities/ Super admin

Le super admin ajoute une nouvelle ville au référentiel. Le nom doit être unique (comparaison insensible à la casse).

GETPOST PATCHDEL /company/stations/ Company admin

CRUD des gares de la compagnie de l'admin courant. La compagnie est automatiquement associée à la création ; le queryset est filtré par compagnie (isolation stricte).

Champs : city, name, address, localisation (coordonnées GPS), + city_name en lecture.

🚐 Module Vehicles

Chaque compagnie gère son parc de véhicules. Un véhicule porte un nombre total de sièges et un plan de sièges (seat_plan) au format JSON, qui décrit la disposition réelle des places : c'est ce plan qui permet à l'auto-attribution et à l'affichage client de savoir quels sièges existent et lesquels sont non commercialisables (chauffeur, hôtesse…). Le statut du véhicule (active / maintenance) conditionne son affectation à des voyages.

GETPOST PATCHDEL /company/vehicles/ Company admin

CRUD du parc de la compagnie. Filtrable par ?status= et ?vehicle_type=. Le nombre de sièges doit être strictement positif.

Champs : registration, brand, model, vehicle_type, total_seats. Le status et le seat_plan ne se modifient pas ici mais via les actions dédiées.

POST /company/vehicles/{id}/maintenance/ · /activate/ Company admin

Bascule le véhicule en maintenance (indisponible pour de nouveaux voyages) ou le réactive. Réponse : le véhicule mis à jour.

GETPUT /company/vehicles/{id}/seat-plan/ Company admin

Lit ou remplace le plan des sièges du véhicule. Le PUT attend un layout (rangées de numéros) et une liste reserved optionnelle.

curl -X PUT http://localhost:8000/api/v1/company/vehicles/5/seat-plan/ \
  -H "Authorization: Bearer <access-admin>" \
  -H "Content-Type: application/json" \
  -d '{ "layout": [[1,2],[3,4],[5,6]], "reserved": [1] }'

🛣️ Module Routes

Une route (trajet type) relie une ville d'origine à une ville de destination, avec un prix de base, une distance et une durée. Elle peut comporter des escales (RouteStop) intermédiaires, chacune avec son propre tarif partiel. Les routes sont le gabarit à partir duquel on génère ensuite des voyages datés (module Trips). Une route et son véhicule doivent appartenir à la même compagnie.

GETPOST PATCHDEL /company/routes/ Company admin

CRUD des trajets de la compagnie. Filtrable par ?origin_city=, ?destination_city=, ?is_active=. La ville de départ et d'arrivée doivent différer.

Champs : origin_city, destination_city, origin_station, destination_station, distance_km, base_price, duration_minutes, is_active. Les stops sont renvoyés en lecture.

POST /company/routes/{id}/duplicate/ Company admin

Crée automatiquement le trajet retour (origine et destination inversées), ce qui évite de ressaisir un aller-retour. Réponse : 201 avec la route créée.

GETPOST PATCHDEL /company/routes/{route_pk}/stops/ Company admin

CRUD des escales d'une route (ressource imbriquée). La route parente est déduite de l'URL et vérifiée contre la compagnie de l'admin.

Champs : city, stop_order (ordre dans le trajet), stop_price (tarif jusqu'à cette escale).

🚌 Module Trips

Un voyage (trip) est l'instance datée d'une route : une route + un véhicule + une heure de départ. C'est l'objet que le voyageur réserve réellement. À la création, le nombre de places disponibles (available_seats) est initialisé depuis le total de sièges du véhicule ; il n'est ensuite jamais fixé à la main mais décrémenté/incrémenté par les réservations sous verrou de ligne. Le prix reprend par défaut le prix de base de la route.

Le module sert trois publics : le public (recherche & détail), l'agent (voyages du jour) et le company admin (CRUD + génération en masse).

🔎 Public — recherche & détail

GET /trips/search/ Public

Recherche des voyages à venir, programmés et ayant assez de places, triés par heure de départ. C'est le moteur de recherche de la page d'accueil.

Query params

ParamEffet
origin_cityid de la ville de départ
dest_cityid de la ville d'arrivée
datedate de départ (YYYY-MM-DD)
passengersnombre de places minimum requis (entier)
max_priceprix maximum

curl "http://localhost:8000/api/v1/trips/search/?origin_city=1&dest_city=2&date=2026-07-10&passengers=2"
GET /trips/{id}/ Public

Détail public d'un voyage, incluant la liste des numéros de sièges encore disponibles (available_seat_numbers) pour permettre au voyageur de choisir sa place.

🧑‍✈️ Agent — voyages du jour

GET /agent/trips/today/ Agent

Liste (non paginée) des voyages du jour rattachés à la gare et/ou au véhicule de l'agent connecté. Sert de plan de travail quotidien au guichet et au contrôle.

🏢 Company admin — gestion des voyages

GETPOST PATCHDEL /company/trips/ Company admin

CRUD des voyages de la compagnie. Filtrable par ?route=, ?status= et ?date=. La suppression n'efface pas : elle annule le voyage (avec reason) et notifie les passagers.

Champs (écriture) : route, vehicle, departure_time, arrival_time, price (optionnel). Le véhicule et la route doivent appartenir à la même compagnie.

POST /company/trips/generate/ Company admin

Génère en masse des voyages à partir d'une route et d'une grille horaire, sur un nombre de jours donné — idéal pour créer un planning hebdomadaire en une requête.

curl -X POST http://localhost:8000/api/v1/company/trips/generate/ \
  -H "Authorization: Bearer <access-admin>" \
  -H "Content-Type: application/json" \
  -d '{ "route_id": 4, "schedule_config": ["08:00", "14:00"], "days": 7 }'

Réponse : 201 { "created": N, "trips": [...] }.

💳 Module Payments

Ce module encaisse le paiement d'une réservation. Le flux est en deux temps : on initie un paiement (statut pending), puis on le confirme. Comme il n'existe pas encore d'intégration directe avec les opérateurs Mobile Money, la référence de transaction est saisie manuellement par l'agent ou le voyageur. À la confirmation, la réservation liée passe à paid et le SMS de confirmation part.

Donnée sensible : la transaction_ref n'est jamais renvoyée en clair — l'API n'expose que ses 4 derniers caractères (****1234).
POST /payments/ Authentifié

Initie un paiement pour une réservation. Reste pending jusqu'à confirmation.

ChampType
booking_idintrequis
methodchoixrequis
phonestringoptionnel

Le paiement de colis (parcel_id) n'est pas encore disponible.

POSTGET /payments/{id}/verify/ · /{id}/receipt/ Authentifié

verify confirme le paiement (saisie de transaction_ref) et bascule la réservation en paid. receipt télécharge le reçu au format PDF. Chaque utilisateur ne voit que les paiements de son périmètre (voyageur : ses réservations ; agent/admin : sa compagnie ; super admin : tout).

POST /agent/payments/ Agent guichet

Encaissement au guichet en une seule étape (initiation + confirmation). La transaction_ref est requise hors espèces. L'agent ne peut encaisser que pour sa compagnie.

curl -X POST http://localhost:8000/api/v1/agent/payments/ \

  -H "Content-Type: application/json" \
  -d '{ "booking_id": 42, "method": "cash" }'

📦 Module Parcels

Au-delà des voyageurs, les compagnies transportent aussi des colis. Ce module couvre tout leur cycle : enregistrement au guichet, calcul automatique du tarif, suivi public par numéro de suivi, notification du destinataire à l'arrivée, puis remise. Le tarif est calculé par le service selon le poids et la tranche de distance (jamais fourni par le client) ; le mode hors ligne est supporté.

Suivi public sécurisé : le suivi utilise le tracking_number (jamais l'id) et masque le téléphone du destinataire (******45).
GET /parcels/track/{tracking_number}/ Public

Suivi public d'un colis : statut courant + historique des événements (enregistré, notifié, remis), sans exposer de données sensibles.

curl http://localhost:8000/api/v1/parcels/track/CB2026000123/
GETPOST /agent/parcels/ · /{id}/notify/ · /arrivals/ Agent guichet

Enregistre un colis au guichet (compagnie & gare de départ déduites du profil agent, tarif calculé par le service). arrivals liste les colis arrivés à la gare de l'agent en attente de notification ; notify envoie le SMS au destinataire (ou enregistre un appel manuel).

Champs création : origin_city, destination_city, destination_station, sender_name/phone, recipient_name/phone, weight_kg, description, + is_offline/offline_created_at.

GETPATCH POST /company/parcels/ · /{id}/status/ · /{id}/notify-again/ · /export/ Company admin

Vue compagnie de tous les colis (filtrable). Permet de corriger les informations (PATCH), de forcer un changement de statut (status), de renvoyer le SMS d'arrivée (notify-again) et d'exporter la liste en Excel/PDF (?format=).

📣 Module Claims

Les réclamations permettent aux voyageurs de signaler un problème (retard, bagage, service…), éventuellement rattaché à une réservation. Le traitement suit une hiérarchie : la compagnie répond en première ligne ; le super admin supervise et peut relancer (escalade) ou clôturer. Une réclamation sans réponse au-delà de 48h est signalée comme is_overdue (indicateur calculé, non stocké), ce qui fait remonter les dossiers en retard en tête de liste.

GETPOST /claims/ Voyageur

Dépose (POST) et consulte (GET) ses propres réclamations. La compagnie visée est soit fournie, soit déduite de la réservation référencée — qui doit appartenir au voyageur.

Champs : company (ou booking), claim_type, subject, description.

GETPOST /company/claims/ · /{id}/respond/ · /stats/ Company admin

Réclamations reçues par la compagnie (les non traitées d'abord). respond apporte une réponse et change le statut ; stats donne le taux de résolution et le délai moyen de traitement.

GETPOST /super/claims/ · /unresolved/ · /{id}/escalate/ · /{id}/close/ Super admin

Supervision transverse. unresolved liste les dossiers non traités toutes compagnies ; escalate relance la compagnie ; close clôture directement.

⭐ Module Reviews

Les avis notent une compagnie (de 1 à 5) après un voyage. Une règle métier stricte s'applique : un avis n'est possible que si le voyage est completed et que le voyageur y a une réservation payée (validé dans le service). Les avis publics n'exposent que le prénom et l'initiale du nom de l'auteur. La compagnie peut répondre publiquement et signaler un avis abusif (qui disparaît alors des listes publiques), mais ne peut jamais le supprimer — seul le super admin le peut.

GETPOST /reviews/ Public / Voyageur

La lecture est publique (avis non signalés, filtrables par ?company_id=) ; le dépôt exige le rôle voyageur. Champs création : trip, rating (1–5), comment.

GETPOST PATCH /company/reviews/ · /{id}/respond/ · /{id}/flag/ · /word-cloud/ Company admin

Tous les avis de la compagnie (signalés inclus). respond répond publiquement ; flag signale un avis au super admin ; word-cloud renvoie la fréquence des mots pour une analyse qualitative. DELETE renvoie 405 (interdit).

🚨 Module Speed Reports

Ce module de sécurité routière permet à un voyageur de signaler un excès de vitesse pendant son trajet, avec une vitesse estimée, une description et, si disponibles, des coordonnées GPS. Les signalements remontent à la compagnie concernée (consultation) et au super admin, qui pilote leur traitement en changeant leur statut. C'est un canal de responsabilisation des transporteurs.

POST /speed-reports/ Voyageur

Dépose un signalement. Horodatage automatique ; GPS optionnel.

Champs : company, trip (optionnel), estimated_speed, description, latitude, longitude.

GET /company/speed-reports/ Company admin

Consultation (lecture seule) des signalements visant la compagnie de l'admin courant.

GETPATCH /super/speed-reports/ · /{id}/ Super admin

Tous les signalements de la plateforme. Le PATCH fait évoluer le statut du dossier (en cours de traitement, résolu, etc.).

💬 Module Messaging

La messagerie interne permet des échanges directs entre utilisateurs (par ex. un agent contactant un voyageur). Chaque utilisateur voit sa boîte (messages envoyés et reçus) ; l'ouverture d'un message reçu le marque automatiquement comme lu. Pour les agents, l'objet du message est obligatoire. Un endpoint dédié fournit la liste des passagers d'un voyage pour faciliter le choix du destinataire.

GETPOST /messages/ · /messages/{id}/ Authentifié

Liste la boîte de l'utilisateur, envoie un message (recipient, subject, body) et lit un message (marqué lu à l'ouverture). On ne peut pas s'écrire à soi-même.

GET /agent/trips/{trip_id}/passenger-list/ Agent

Liste des passagers d'un voyage (id, nom complet, téléphone), restreinte à la compagnie de l'agent. Pratique pour sélectionner un destinataire ou contacter les voyageurs d'un départ.

🔔 Module Notifications

Les notifications in-app informent l'utilisateur d'événements le concernant (réservation confirmée, colis arrivé, réponse à une réclamation…). Elles sont propres à chaque utilisateur, triées avec les non lues en premier, et peuvent être marquées comme lues individuellement ou en bloc. Chaque notification porte une référence (reference_id / reference_type) permettant au client de rebondir vers l'objet concerné.

GETPOST /notifications/ · /{id}/read/ · /read-all/ Authentifié

Liste les notifications de l'utilisateur (non lues d'abord). read marque une notification comme lue ; read-all les marque toutes et renvoie le nombre mis à jour.

curl -X POST http://localhost:8000/api/v1/notifications/read-all/ \
  -H "Authorization: Bearer <access>"
# → { "updated": 5 }

📶 Module Sync — mode hors ligne

C'est la pierre angulaire de la contrainte métier « les agents travaillent sans internet ». Le module permet à un agent de récupérer un paquet de travail quand il a du réseau, de travailler hors ligne toute la journée (ventes, colis, embarquements enregistrés localement), puis de synchroniser le tout en un seul appel atomique dès que la connexion revient.

Idempotence & résolution de conflits : le ticket_number / tracking_number généré localement sert de clé d'idempotence. En cas de conflit de siège (deux agents ayant vendu la même place hors ligne), le serveur réattribue automatiquement le prochain siège libre et journalise le conflit en français.
GET /agent/offline-data/ Agent

Renvoie le paquet de travail du jour : voyages (avec plan de sièges), réservations associées et colis arrivés en attente de remise. À télécharger avant de passer hors ligne.

{ "trips": [...], "bookings": [...], "parcel_arrivals": [...] }
POST /agent/sync/ Agent

Synchronise en une transaction atomique les lots saisis hors ligne : bookings, parcels, validations (embarquements). Chaque élément porte son offline_created_at et son numéro généré localement.

curl -X POST http://localhost:8000/api/v1/agent/sync/ \
  -H "Authorization: Bearer <access-agent>" \
  -H "Content-Type: application/json" \
  -d '{
    "bookings": [
      { "ticket_number": "BF2026009001", "trip_id": 7,
        "first_name": "Ali", "last_name": "Traore", "phone": "+22670000001",
        "offline_created_at": "2026-07-02T09:30:00Z" }
    ],
    "parcels": [], "validations": []
  }'

Réponse — 200 OK

{
  "synced": { "bookings": 1, "parcels": 0, "validations": 0 },
  "conflicts": [
    { "entity": "booking", "reference": "BF2026009001",
      "original_seat": "12", "assigned_seat": "15",
      "resolution": "Siege 12 deja pris, reattribue au 15." }
  ],
  "errors": []
}
GET /agent/sync/logs/ · /agent/sync/conflicts/ Agent

logs retourne l'historique des synchronisations (compteurs + conflits par session) ; conflicts retourne les conflits résolus lors de la dernière synchronisation, pour affichage immédiat à l'agent.

📊 Module Dashboard

Ce module regroupe des endpoints en lecture seule qui agrègent des indicateurs pour chaque type d'utilisateur. Il ne possède aucun modèle propre : chaque vue délègue les calculs à services.py. Toutes les réponses sont mises en cache 5 minutes et varient sur l'en-tête Authorization, garantissant qu'un cache n'est jamais servi d'un utilisateur à un autre (isolation multi-tenant préservée).

Les tableaux de bord compagnie et super acceptent une période via ?period=day|week|month ou une plage explicite ?start_date=&end_date= (format AAAA-MM-JJ).

🧳 Voyageur

GET /dashboard/traveler/ — prochains voyages, nombre de réservations actives / en attente, dernières notifications.

🧑‍✈️ Agent

GET /agent/dashboard/ — prochains départs, alertes en attente, statut de connexion.

🏢 Company admin

GET /company/dashboard/ — KPI (recette, taux de remplissage, réservations, note) avec comparaison à la période précédente.

🛡️ Super admin

GET /super/dashboard/ — vue plateforme : compagnies, réservations, commission, utilisateurs actifs.

GET /company/dashboard/{revenue-chart|fill-rate-by-route|payment-breakdown|top-routes|agent-activity|alerts}/ Company admin

Séries et répartitions détaillées de la compagnie : recettes dans le temps, taux de remplissage par trajet, répartition des paiements, top 5 des trajets, activité du jour par agent, et compteurs d'alertes opérationnelles (réclamations non résolues, colis non remis, signalements en attente).

GET /company/dashboard/export/?format=pdf|excel Company admin

Rapport complet (synthèse + top trajets + paiements) généré à la volée en Excel ou PDF (repli CSV si openpyxl absent). Non mis en cache.

GET /super/dashboard/{revenue-by-company|bookings-chart}/ Super admin

Vues transverses : recettes et commissions par compagnie, et évolution du volume global de réservations dans le temps.

💡 Améliorations proposées

Pistes issues de la lecture du code, à valider avec l'équipe avant implémentation :

📄 OpenAPI / Swagger UI

drf-spectacular est déjà utilisé (@extend_schema). Exposer /api/v1/schema/ + Swagger UI & Redoc génère une doc interactive « essayez-la » toujours à jour.

🔁 Idempotency-Key

Sur POST /bookings/ et /agent/bookings/, accepter un en-tête Idempotency-Key évite les doublons en cas de retry réseau (fréquent en connexion instable).

📶 Endpoint /health & /version

Utile pour le monitoring et pour que les apps agents détectent le retour de connexion avant de synchroniser.

🌐 i18n des messages

Les messages sont en français non accentué (« Paye »). Passer par gettext permettrait accents corrects + support mooré/dioula à terme.

🔎 Recherche & tri voyageur

Ajouter ?status= et un tri sur /bookings/ côté voyageur (aujourd'hui seul l'admin filtre).

🧾 Pagination de l'export

L'export itère tout le queryset en mémoire. Un export asynchrone via Celery (déjà présent) + lien de téléchargement éviterait les timeouts sur gros volumes.

⏱️ Rate limiting élargi

Étendre le throttling au scan et à la création de réservation pour limiter l'abus, avec en-têtes Retry-After normalisés sur les 429.

🔐 Réponses d'erreur unifiées

Un exception handler DRF renvoyant toujours { "code", "detail", "field_errors" } faciliterait la gestion d'erreurs côté clients mobiles.
